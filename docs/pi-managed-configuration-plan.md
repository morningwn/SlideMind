## 目标与边界

2026-09-16：用户明确要求 Web 直接切换，已移除 pi-web-access 并内置四个 Web 工具，固定使用 Exa 无 Key 公共接口，不读取旧搜索配置、环境凭据或浏览器资料。正文提取复用 Readability/linkedom 和 Tika；缓存按会话及当前分支授权。无双实现和自动回退。行为差异与验证边界见 [Web 工具实施记录](pi-web-tools-plan.md)，不据此认定 Pi 核心和权限配置已隔离。

采用“应用统一管理配置 + 非必要能力移除 + 简单必要能力自研 + 复杂必要能力按需适配”，关闭 Pi 核心与扩展的外部配置自动发现，保留必要的 Agent 能力。

允许的配置来源仅包括应用默认值、用户通过 SlideMind 设置界面保存的配置，以及应用安全存储中的凭据。

禁止自动读取用户原有 Pi 配置目录、项目 `.pi/` 下的设置与权限策略、外部扩展与 Skill、外部 `AGENTS.md` / `SYSTEM.md` / `APPEND_SYSTEM.md`，以及服务商凭据环境变量、外部工具登录信息和历史配置回退路径。

该边界针对自动配置发现和提示词注入。用户明确要求阅读项目文档时，仍按文件权限处理；会话、任务清单和缓存属于运行数据，继续保留。操作系统正常运行所需的环境信息不在一概禁用范围内，但不得作为 Agent 业务配置的隐式来源。

仅迁移配置目录不足以完成隔离，必须同时关闭项目配置合并、环境变量覆盖、用户凭据发现和历史路径回退。

2026-09-16 核查的公开源码展示了不同集成方式，不代表整个 Pi 生态采用统一方案。链接指向可变的上游分支，仅用于架构参考；具体 API 以本项目固定版本为准。

| 参考                                                                                                                                        | 已核实的做法                                                                 | 适用边界                                                                                     |
| ------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| [OpenClaw Worker](https://github.com/openclaw/openclaw/blob/main/src/worker/embedded-agent.runtime.ts)                                      | 内存设置、凭据与模型注册表；关闭默认扩展和资源发现；显式提供宿主工具及白名单 | 仅说明该 Worker 路径。它仍由宿主主动读取选定的 AGENTS.md，不能视为整个项目完全不读取外部配置 |
| [Prime Agent 会话服务](https://github.com/PrimeIntellect-ai/prime-agent/blob/main/packages/coding-agent/src/core/agent-session-services.ts) | 合并内置与用户扩展工厂，保留资源加载器以及文件配置能力                       | 适合保留用户扩展生态的通用 Agent，不直接满足 SlideMind 的隔离目标                            |
| [Pi SDK](https://github.com/badlogic/pi-mono/blob/main/packages/coding-agent/docs/sdk.md)                                                   | 支持内联 extensionFactories、自定义工具和 ResourceLoader                     | 自研能力可以直接注册为应用模块，无需包装成外部插件包                                         |

SlideMind 选择宿主控制的嵌入式集成：复用 Pi 的模型调用、工具循环、会话和原生压缩，由应用决定配置、凭据、资源及工具权限。产品能力通过内部工厂显式注册，第三方扩展仅作为可选实现依赖，不开放用户扩展自动发现。本项目不跟随 OpenClaw Worker 主动加载外部 AGENTS.md。

公开样本支持显式注入与应用内置能力的可行性，但不证明当前安装的第三方扩展已经支持配置注入，也不构成运行时全局 fs 拦截的依据。

## 配置与存储设计

配置流向为：应用设置界面 → 主进程配置服务与安全凭据存储 → Pi 会话及应用管理的扩展。

- 配置服务统一负责默认值、输入校验、版本迁移和持久化。
- 扩展接收必要的配置对象、凭据访问函数及状态存储接口，不自行寻找配置来源。
- 继续复用现有加密凭据存储，不增加明文 Key 文件，不向渲染进程暴露凭据。
- Pi 设置使用内存实例，模型由应用注册。
- 每个会话使用明确的配置快照；配置更新原则上在下一次任务执行时生效，实施时验证既有会话如何重建或更新。
- 运行数据保存在应用 userData 下，按扩展划分目录，与业务配置区分。
- 不改写 HOME，不通过临时修改进程环境实现隔离。
- 第一阶段不扩展大量设置项，未开放选项由应用默认值控制。

### 宿主初始化与生命周期

主进程先生成配置快照和凭据访问接口，再创建 Pi 服务及应用能力工厂，最后建立会话。资源加载器只提供应用显式列出的内置 Skill、提示词、工具与扩展；不保留默认扫描作为兜底。简单工具可直接注册为自定义工具，需要事件钩子的能力使用 ExtensionFactory。

同一次会话创建中，资源加载器与会话必须共享受控的设置来源。优先使用无需文件读取的内存实现；如默认资源加载器仍包含无法关闭的发现逻辑，再实现限定职责的 ResourceLoader，而非全局修改文件系统或重写整个 Agent。

配置生命周期须覆盖首次创建、资源 reload、会话恢复、分支及下一次任务执行。曾有 [OpenClaw 问题报告](https://github.com/openclaw/openclaw/issues/65602) 指出资源 reload 重置压缩设置；这是需要测试的失效模式，不代表本项目或其当前版本已确认存在相同缺陷。必须验证配置不会在重载时回退到文件或 SDK 默认值，事件钩子不会重复注册，不同会话的配置不会通过模块全局变量互相污染。

## 选型原则

不以保留当前扩展数量为目标。先确定产品必需的可观察行为，再选择实现方式：

1. 非必要能力默认移除，不为替代一个不需要的插件而重新实现它。
2. 必要且边界清楚、实现与维护成本低的能力优先自研，注册为应用内部 ExtensionFactory。
3. Pi SDK 或项目已有能力可以满足需求时直接复用，不重复实现。
4. 必要但复杂的能力优先增加显式依赖注入入口；差异较小时使用固定版本的 pnpm 补丁，改动分散时才 Fork。
5. 成本评估包含异常处理、安全边界、旧会话兼容、测试和升级，不以代码行数判断简单程度。

下面的复杂度和选型属于方案判断，尚未完成原型验证。移除前必须证明无必要行为依赖；发现与产品要求冲突时记录缺口并调整方案，不能静默削减功能。

### Todo 实施设计

2026-09-16 对照 [Pi 当前 SDK 分支的 Todo 示例](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/examples/extensions/todo.ts)、[OpenCode 的工具](https://github.com/anomalyco/opencode/blob/dev/packages/opencode/src/tool/todo.ts)与[会话存储](https://github.com/anomalyco/opencode/blob/dev/packages/opencode/src/session/todo.ts)、[Codex 的计划工具契约](https://github.com/openai/codex/blob/main/codex-rs/core/src/tools/handlers/plan_spec.rs)。这些链接指向可变分支，只证明所查看实现的取舍。SlideMind 的任务清单跟随 Pi 会话分支，且界面只使用标题、状态和进行中提示；因此选择 Pi 式会话快照，不另建数据库，也不照搬 OpenCode 的整表更新作为唯一操作。

- 保留工具名 `todo`，由应用内部 ExtensionFactory 注册。新工具提供 `replace`、`add`、`update`、`list`：`replace` 接收完整的 `{ subject, status, activeForm? }[]`，明确重建清单，空数组表示清空；`add` 接收标题和可选进行中提示，新任务默认为待处理；`update` 接收 ID 和至少一个待修改字段；`list` 无额外参数。日常进度变更使用 `update`，避免模型重传整份清单时意外漏项。旧 `create/get/delete/clear` 操作及原扩展的配置、终端交互、依赖图、负责人和元数据不进入新契约。
- 任务仅保留应用实际使用的 `id`、`subject`、`status` 和可选 `activeForm`；状态为 `pending`、`in_progress`、`completed`。ID 由宿主单调分配，`replace` 为新清单分配新 ID；已完成项允许重新打开以处理返工。输入要求标题非空、状态合法、更新目标存在，并限制数量及文本长度；同一清单最多一项 `in_progress`。无效调用不改变状态，以工具错误返回明确原因。
- 每次成功调用都在工具结果 `details` 写入带版本号的完整任务快照和 `nextId`，包括 `list` 与空清单。每个会话的内存状态由自己的扩展实例持有；会话启动、资源重载、压缩和分支切换时从当前分支最后一个有效快照重建。任务清单属于会话运行数据，不读取外部 Todo 配置，也不另存可与会话分支冲突的状态文件。
- 旧会话仅兼容读取 `rpiv-todo` 已记录的 `details.tasks` 快照，转换界面所需字段并保留可用 ID；不保留旧工具调用接口，不改写或删除旧会话。新旧快照按当前分支时间顺序选择最后一个有效值。工具成功后继续通过现有主进程事件链更新界面，清空时也必须发送空数组；会话恢复及分支切换后同步当前分支的清单。
- 验证 `replace → add → update → list`、返工、ID 连续性、非法状态、第二个进行中任务、空清单事件、有效旧快照的只读恢复、压缩与分支回放、资源重载及并行会话隔离。新工具契约和旧快照转换通过测试后，再移除 `@juicesharp/rpiv-todo` 的加载入口和依赖，执行干净安装与打包验证。有效旧快照的恢复失败视为替换未通过，而不是静默显示空清单。

### 自研边界

- Todo 复用现有 `agent-todo` 的事件和界面投影；旧快照只读恢复，工具操作按上述新契约实现。
- Continue 不重新实现通用上下文压缩引擎。用接近上下文上限的多阶段 PPT 任务验证原生压缩后能否恢复当前阶段、Todo、产物位置和下一步；优先复用会话、任务清单和 workflow-status.md 中已有状态，仅补充必要续接信息。续接不等同于崩溃恢复或后台运行，不扩大交付范围。
- 缓存优化不预设移除后性能不变。当前扩展会重排和精简提示词、调整部分请求参数，并非仅展示统计。使用相同模型、任务和受控上下文比较启用与禁用后的输出正确性、缓存命中、输入费用和延迟，记录服务端缓存状态对结果的影响，不凭单次结果判断。若收益明确，仅保留必要的提示词稳定化或参数适配；应用现有用量统计独立保留。实际模型调用与费用遵循项目授权要求。
- 权限规则固定在应用代码或受控配置中。覆盖目录越界、符号链接、只读 Skill、未知工具、原生及自定义工具；不能只检查工具名称。新增工具必须纳入同一授权边界。
- Web 最小实现仍须包含取消、超时、结果大小限制、重定向及网络地址校验、错误报告和结果引用。搜索服务的选择、凭据与使用成本须明确，不能偷偷依赖本机凭据，也不默认新增付费服务。
- Web 的 source_check 等语义须从现有调用方和 Skill 提取后确认，不能用空实现、固定成功或简单别名冒充兼容。
- 应用实现放在现有 Agent 模块内；没有独立发布或复用需求时，不为了替换扩展而新增包管理体系。

## 注入与第三方适配

现有扩展没有统一的宿主配置注入接口。通过 ExtensionFactory 注册只解决实例创建，不会自动阻止扩展内部文件读取。

- 应用显式注入配置快照、凭据访问函数及运行状态存储；缺少必需配置时报告错误，不回退用户目录或环境变量。
- 注入必须在首次配置读取之前完成。Free 的 config.js 在模块顶层初始化用户文件，缓存扩展也在模块顶层读取配置，须移除这些副作用。
- Continue 除自身配置外，还独立读取 Pi 压缩设置及提示词覆盖文件；权限系统另有旧 settings 与 MCP 配置入口；Web 的服务商模块自行读取凭据。适配须覆盖整个调用链。
- 不使用运行时全局 fs 拦截、模块缓存替换或临时环境修改管理配置；文件访问拦截仅用于隔离测试。
- 必要的少量第三方修改优先使用 pnpm 固定版本补丁，补丁与锁文件一同提交。验证首次安装、构建和打包，不手改 node_modules。
- 只有改动分散、补丁难维护且能力确实必要时，才转为仓库内 Fork，记录上游版本和提交、保留归属及许可证、同步第三方声明。
- 第三方升级必须审查新增读取入口并执行隔离回归；构建时 alias 不视为动态扩展加载已经被替换的证据。

## 实施阶段

### 第一阶段：行为基线与入口清单

列出配置、凭据、状态和资源读取入口，包括模块导入、会话启动、工具执行和重载阶段。补齐工具名称、输入输出、会话恢复与权限行为测试，确认 pi-free 的实际作用。明确所有配置与状态路径的归属。为每项能力记录必需性、调用方、SDK 可替代性、删除影响及验收用例；特别确认搜索服务来源、权限覆盖范围和原生压缩能力。

### 第二阶段：Pi 核心隔离

建立统一配置服务并注入内存设置与凭据。仅加载内置 Skill 和显式注册扩展，关闭附加提示词发现，同步 Skill 列表与 README。变更内置 Skill 加载契约时同步 bundled-skills 测试。

在迁移第三方扩展前，先验证宿主初始化和重载路径中的设置来源一致；只在关闭发现的默认加载器不足以满足边界时增加自定义 ResourceLoader。

### 第三阶段：逐扩展接管

先按上述设计自研 Todo，验证无需外部配置及历史会话只读恢复。Free、缓存扩展和 Continue 的处理进度见实施记录。权限和 Web 分别完成可行性原型与行为测试，再选择自研或适配；权限替代通过前不得关闭现有保护。

每项完成后删除不再使用的扩展加载入口、配置准备逻辑和依赖，更新扩展数量断言、工具契约、相关 Skill/reference、bundled-skills 测试和 README。删除依赖不等于删除用户历史数据。每次只替换一个能力，验证通过后再处理下一项。

### 第四阶段：设置与存储收口

移除旧配置合并、缺失回退及环境变量覆盖。继续使用已有应用凭据，不自动导入外部配置，不删除旧文件。明确配置快照的更新策略。

### 第五阶段：集成与打包验收

验证开发态与打包后资源路径、扩展加载、会话恢复及核心 Agent 工作流；记录实际测试平台及未验证范围。

## 验收标准

- 在用户目录、项目目录和历史位置放置带标记配置后，设置、提示词、工具及权限不受影响。
- 注入外部服务商环境变量后，模型、凭据、搜索服务和扩展行为不发生变化。
- 对禁止路径进行文件访问监测，确认不是读取后忽略；测试覆盖模块导入及延迟执行路径。
- 应用设置可以生效，凭据不进入日志或渲染进程。
- 首次创建、资源重载、会话恢复、分支与下一次执行后，应用配置仍保持预期值，不回退文件配置；并行会话之间无配置串扰，事件钩子不会重复注册。
- 缓存优化移除或替代须附对照测量及结论；Continue 移除或替代须验证压缩后阶段、待办及产物状态的恢复，不能只验证请求成功。
- 新 Todo 工具契约、历史任务清单只读恢复、原生或自研的压缩续接与权限规则通过回归测试；移除的非必要功能明确记录。
- 权限替代方案通过越界、符号链接、只读资源和未知工具等负向测试；Web 替代方案通过取消、超时、重定向和网络边界测试。
- 删除配置或外部环境变量后仍能按应用配置运行；卸载不再需要的扩展后完成干净安装及打包验证。
- 完成针对性单元测试、pnpm test、TypeScript 检查、pnpm format:check 和打包冒烟验证。
- 测试使用隔离临时目录与虚构凭据，不读取或改写真实用户配置。

静态扫描用于发现遗漏，运行测试用于验证覆盖到的实际路径。不能仅凭路径搜索结果宣布完全隔离。

## 风险与回滚

主要风险包括遗漏隐式读取、旧会话不兼容、第三方行为回归、自研安全遗漏、搜索服务依赖及持续维护适配代码的成本。采用版本固定、逐扩展迁移和契约测试控制风险。

每阶段保持独立变更，不删除外部配置或历史会话。发生回归可回退对应代码与依赖版本；回退旧版本可能恢复外部配置读取，必须明确记录。避免第一阶段引入不可逆的数据格式迁移。

## 授权与范围

该方案涉及配置体系和依赖组织的系统性调整，执行前须按仓库规则获得明确确认。实施不包含发布、部署、向外部仓库推送或新增收费服务。发现必须明显偏离方案时，先说明替代方案与影响，再确认相关变更。
