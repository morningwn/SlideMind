# Pi Agent 配置统一管理方案

日期：2026-09-16。

状态：方案草案，尚未实施。保存本方案不代表已批准系统性改造。

## 目标与边界

采用“应用统一管理配置 + 非必要能力移除 + 简单必要能力自研 + 复杂必要能力按需适配”，关闭 Pi 核心与扩展的外部配置自动发现，保留必要的 Agent 能力。

允许的配置来源仅包括应用默认值、用户通过 SlideMind 设置界面保存的配置，以及应用安全存储中的凭据。

禁止自动读取用户原有 Pi 配置目录、项目 `.pi/` 下的设置与权限策略、外部扩展与 Skill、外部 `AGENTS.md` / `SYSTEM.md` / `APPEND_SYSTEM.md`，以及服务商凭据环境变量、外部工具登录信息和历史配置回退路径。

该边界针对自动配置发现和提示词注入。用户明确要求阅读项目文档时，仍按文件权限处理；会话、任务清单和缓存属于运行数据，继续保留。操作系统正常运行所需的环境信息不在一概禁用范围内，但不得作为 Agent 业务配置的隐式来源。

仅迁移配置目录不足以完成隔离，必须同时关闭项目配置合并、环境变量覆盖、用户凭据发现和历史路径回退。

## 配置与存储设计

配置流向为：应用设置界面 → 主进程配置服务与安全凭据存储 → Pi 会话及应用管理的扩展。

- 配置服务统一负责默认值、输入校验、版本迁移和持久化。
- 扩展接收必要的配置对象、凭据访问函数及状态存储接口，不自行寻找配置来源。
- 继续复用现有加密凭据存储，不增加明文 Key 文件，不向渲染进程暴露凭据。
- Pi 设置使用内存实例，模型由应用注册。
- 每个会话使用明确的配置快照；配置更新原则上在下一次任务执行时生效，实施时验证既有会话如何重建或更新。
- 运行数据保存在应用 userData 下，按扩展划分目录，与业务配置区分。
- 不改写 HOME，不通过临时修改进程环境实现隔离。
- 第一阶段不扩展大量设置项，未开放选项由应用默认值控制。

## 选型原则

不以保留当前扩展数量为目标。先确定产品必需的可观察行为，再选择实现方式：

1. 非必要能力默认移除，不为替代一个不需要的插件而重新实现它。
2. 必要且边界清楚、实现与维护成本低的能力优先自研，注册为应用内部 ExtensionFactory。
3. Pi SDK 或项目已有能力可以满足需求时直接复用，不重复实现。
4. 必要但复杂的能力优先增加显式依赖注入入口；差异较小时使用固定版本的 pnpm 补丁，改动分散时才 Fork。
5. 成本评估包含异常处理、安全边界、旧会话兼容、测试和升级，不以代码行数判断简单程度。

下面的复杂度和选型属于方案判断，尚未完成原型验证。移除前必须证明无必要行为依赖；发现与产品要求冲突时记录缺口并调整方案，不能静默削减功能。

## 扩展选型

| ---------- | -------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Pi 核心    | 复用 SDK，显式注入               | 内存设置与凭据、应用模型注册、关闭自动发现；优先不 Fork 核心                                                                                                                                                                       |
| Todo       | 自研精简扩展                     | 保留当前 todo 工具契约、任务事件、历史会话恢复和分支行为；不复制终端 UI、快捷键或用户配置系统                                                                                                                                      |
| Free       | 优先移除，不自研替代             | 当前仅提供 DeepSeek；检查路由、重试、提供商注册等是否有实际必要依赖，缺少的必要行为优先复用 SDK                                                                                                                                    |
| 缓存优化   | 优先移除，必要部分小范围自研     | 保留应用已有用量统计；缓存优化扩展与服务商自身缓存须分别验证。仅在有测量依据时实现必要的请求参数适配，不复制多服务商优化、终端展示或统计系统                                                                                       |
| Continue   | 优先复用 Pi 压缩；必要时自研薄层 | 先验证原生压缩与长任务续接是否满足产品需求；仅补充已证实缺失的任务状态保留或续接提示。若必须保留复杂续接行为且实现成本高，再适配上游                                                                                               |
| 权限系统   | 必须保留能力，条件性自研         | 先验证能否用应用固定策略与主进程已有边界完整替代。覆盖工具默认拒绝、项目路径、只读资源及所有工具执行路径；未通过安全等价测试前保留并适配现有扩展，不直接移除                                                                       |
| Web Access | 评估自研限定能力，复杂路径适配   | 产品必要能力按现有 web_search、source_check、fetch_content、get_search_content 调用方核查。优先复用项目已有网络与文档能力，实现固定搜索服务、内容获取及结果缓存；不承诺完整 Web 抓取是低成本，无可用服务或存在复杂缺口时保留适配版 |

### 自研边界

- Todo 复用现有 agent-todo 的事件与恢复契约；如需调整数据结构，提供兼容读取，避免历史任务丢失。
- Continue 不重新实现通用上下文压缩引擎。用接近上下文上限的长任务验证需求，再决定是否增加扩展。
- 缓存优化不预设移除后性能不变，比较相同模型和任务的正确性、用量与延迟；没有必要收益依据时不保留自定义优化。
- 权限规则固定在应用代码或受控配置中。覆盖目录越界、符号链接、只读 Skill、未知工具、原生及自定义工具；不能只检查工具名称。新增工具必须纳入同一授权边界。
- Web 最小实现仍须包含取消、超时、结果大小限制、重定向及网络地址校验、错误报告和结果引用。搜索服务的选择、凭据与使用成本须明确，不能偷偷依赖本机凭据，也不默认新增付费服务。
- Web 的 source_check 等语义须从现有调用方和 Skill 提取后确认，不能用空实现、固定成功或简单别名冒充兼容。
- 应用实现放在现有 Agent 模块内；没有独立发布或复用需求时，不为了替换扩展而新增包管理体系。

## 注入与第三方适配

现有扩展没有统一的宿主配置注入接口。通过 ExtensionFactory 注册只解决实例创建，不会自动阻止扩展内部文件读取。

- 应用显式注入配置快照、凭据访问函数及运行状态存储；缺少必需配置时报告错误，不回退用户目录或环境变量。
- 注入必须在首次配置读取之前完成。Free 的 config.js 在模块顶层初始化用户文件，缓存扩展也在模块顶层读取配置，须移除这些副作用。
- Continue 除自身配置外，还独立读取 Pi 压缩设置及提示词覆盖文件；权限系统另有旧 settings 与 MCP 配置入口；Web 的服务商模块自行读取凭据。适配须覆盖整个调用链。
- 不使用运行时全局 fs 拦截、模块缓存替换或临时环境修改管理配置；文件访问拦截仅用于隔离测试。
- 必要的少量第三方修改优先使用 pnpm 固定版本补丁，补丁与锁文件一同提交。验证首次安装、构建和打包，不手改 node_modules。
- 只有改动分散、补丁难维护且能力确实必要时，才转为仓库内 Fork，记录上游版本和提交、保留归属及许可证、同步第三方声明。
- 第三方升级必须审查新增读取入口并执行隔离回归；构建时 alias 不视为动态扩展加载已经被替换的证据。

## 实施阶段

### 第一阶段：行为基线与入口清单

列出配置、凭据、状态和资源读取入口，包括模块导入、会话启动、工具执行和重载阶段。补齐工具名称、输入输出、会话恢复与权限行为测试，确认 pi-free 的实际作用。明确所有配置与状态路径的归属。为每项能力记录必需性、调用方、SDK 可替代性、删除影响及验收用例；特别确认搜索服务来源、权限覆盖范围和原生压缩能力。

### 第二阶段：Pi 核心隔离

建立统一配置服务并注入内存设置与凭据。仅加载内置 Skill 和显式注册扩展，关闭附加提示词发现，同步 Skill 列表与 README。变更内置 Skill 加载契约时同步 bundled-skills 测试。

### 第三阶段：逐扩展接管

先自研 Todo，验证显式配置注入和历史会话兼容。随后按第一阶段证据移除无必要依赖的 Free 与缓存扩展，验证原生压缩后决定 Continue 是否需要自研薄层。权限和 Web 分别完成可行性原型与行为测试，再选择自研或适配；权限替代通过前不得关闭现有保护。

每项完成后删除不再使用的扩展加载入口、配置准备逻辑和依赖，更新扩展数量断言、工具契约、相关 Skill/reference、bundled-skills 测试和 README。删除依赖不等于删除用户历史数据。每次只替换一个能力，验证通过后再处理下一项。

### 第四阶段：设置与存储收口

移除旧配置合并、缺失回退及环境变量覆盖。继续使用已有应用凭据，不自动导入外部配置，不删除旧文件。明确配置快照的更新策略。

### 第五阶段：集成与打包验收

验证开发态与打包后资源路径、扩展加载、会话恢复及核心 Agent 工作流；记录实际测试平台及未验证范围。

## 验收标准

- 在用户目录、项目目录和历史位置放置带标记配置后，设置、提示词、工具及权限不受影响。
- 注入外部服务商环境变量后，模型、凭据、搜索服务和扩展行为不发生变化。
- 对禁止路径进行文件访问监测，确认不是读取后忽略；测试覆盖模块导入及延迟执行路径。
- 应用设置可以生效，凭据不进入日志或渲染进程。
- 保留的工具契约、历史任务清单恢复、原生或自研的压缩续接与权限规则通过回归测试；移除的非必要功能明确记录。
- 权限替代方案通过越界、符号链接、只读资源和未知工具等负向测试；Web 替代方案通过取消、超时、重定向和网络边界测试。
- 删除配置或外部环境变量后仍能按应用配置运行；卸载不再需要的扩展后完成干净安装及打包验证。
- 完成针对性单元测试、pnpm test、TypeScript 检查、pnpm format:check 和打包冒烟验证。
- 测试使用隔离临时目录与虚构凭据，不读取或改写真实用户配置。

静态扫描用于发现遗漏，运行测试用于验证覆盖到的实际路径。不能仅凭路径搜索结果宣布完全隔离。

## 风险与回滚

主要风险包括遗漏隐式读取、旧会话不兼容、第三方行为回归、自研安全遗漏、搜索服务依赖及持续维护适配代码的成本。采用版本固定、逐扩展迁移和契约测试控制风险。

每阶段保持独立变更，不删除外部配置或历史会话。发生回归可回退对应代码与依赖版本；回退旧版本可能恢复外部配置读取，必须明确记录。避免第一阶段引入不可逆的数据格式迁移。

## 授权与范围

该方案涉及配置体系和依赖组织的系统性调整，执行前须按仓库规则获得明确确认。实施不包含发布、部署、向外部仓库推送或新增收费服务。发现必须明显偏离方案时，先说明替代方案与影响，再确认相关变更。
