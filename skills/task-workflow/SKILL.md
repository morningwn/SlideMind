# 分步执行与本地任务记录

按用户要求确定交付内容与完成标准，不能把一般文章、方案或报告转换为演示任务。简单且可直接完成的任务直接交付。

## 先确定是否需要流程

- 分析、解释、概括、关键词和局部润色默认在对话中交付。引用 PDF、项目里已有教案或历史上做过 PPT，都不授权新建文件。
- 判断复杂度依据用户要求的工作量、阶段依赖和整体可行性，不依据自己增加的步骤。一次文档读取失败不构成建立项目的理由；简单问答材料不足时说明缺口并请求必要材料，不擅自扩大为检索、成稿、排版、导出的流水线。
- 复杂任务的本地记录只用于记录用户实际要求，不意味着还应生成报告、PPT 或其他未请求的交付物。用户要求只在对话中回答或不写文件时，计划和状态也保留在对话中。
- 只有用户要求继续同一任务才恢复其记录。历史状态、模型曾经自行生成的文件不能替代用户授权；重复提问和纠正方向时重新判断交付方式，不把旧流程的终态当成本轮目标。

例如：“结合这篇课文分析精神”应直接回答有据可查的分析；“概括为四字词语”应压缩为关键词；“保存为分析文档”才写文档；“把上述内容制作成 PPT”才交由 PPT 总控。要求逐句穷尽、跨多份材料核对或长篇多章节交付时，先说明分步方案，再按本 Skill 维护覆盖范围与进度。

## 开始与规划

1. 恢复已有任务时先读取其状态文档和相关产物，核对文件实际内容；结合用户最新指令修正过时状态，不能仅凭会话摘要判断完成。
2. 执行前告知用户将分步完成，说明每步目标、交付物、依赖、验证方法和关键不确定性。步骤按任务需要确定，不套固定阶段数。
3. 可行性不明确时先安排最小验证，例如检查材料是否可读、证据是否足够、工具能否生成所需格式。失败时记录依据与影响，不用未经授权的格式或简化产物替代要求。
4. 在当前项目内建立或更新任务文档，再执行后续步骤。优先使用用户指定目录或交付文件的父目录，否则使用稳定的 `<topic>-work/`；无明确主题时用 `writing-task/`。同名目录属于其他任务时选择未占用的后缀，不覆盖无关文件。状态文件使用 `task-status.md`，产物放在同一目录或引用已有路径，不移动用户原始材料。

## 记录契约

`task-status.md` 至少保存以下当前信息，按任务规模精简篇幅：

- 用户要求：目标、范围、格式、约束和完成标准，保留最新范围调整。
- 输入材料与产物：项目相对路径、来源、已核实内容、假设和待确认问题。
- 步骤清单：稳定的步骤标识、目标、依赖、产物路径、状态、验证方法及实际结果。
- 当前状态、已完成内容、剩余工作、阻塞依据与影响、下一步和恢复条件、最近更新时间。

步骤状态使用 `pending`、`in-progress`、`completed`、`blocked`、`awaiting-user` 或 `stale`。开始执行、完成验证、遇到阻塞、范围变更及本轮结束前都更新文档；不能把计划中的产物记录成已生成。模型自检不等于用户批准。上游内容改变时，将受影响的下游步骤标记为 `stale`，重新检查后才能恢复完成状态。

使用已提供的 `read`、`write`、`edit` 工具维护文档，更新已有文件前先读取。可用 `todo` 同步当前步骤，但会话内清单不能替代本地记录。文件写入失败时报告实际失败和待保存内容，不宣称已经落盘。用户明确要求不写文件时遵从其要求，说明状态仅保留在对话中，不创建任务文档。

## 推进与交付

在授权范围内通过一步的验证后继续下一步，不因分步而强制逐阶段确认。关键歧义、材料缺失或能力不足阻塞某步时，记录问题并请求必要信息，继续不依赖该问题的已授权工作；需要改变交付范围或格式时由用户决定。阶段性成果明确标为阶段成果，不将任务标记为整体完成。

结束前逐项核对用户要求与实际产物，检查事实、引用、完整性和格式；记录已执行的验证及未验证部分。最终回复给出交付内容或文件路径、任务文档路径、实际检查结果和剩余问题。只有约定交付全部完成且相关验证通过时，才记录整体完成。

## 与 PPT 流程协作

只有用户要求演示工作时，按交付层级选择已注册的 PPT Skill。完整演示的阶段与质量门禁仍由 `ppt-production-workflow` 管理，直接在其 `workflow-status.md` 补充上述任务信息，不再为同一演示维护重复的 `task-status.md` 或复制其状态机。混合任务可保留总任务文档，引用演示子任务的状态文档，不复制子任务阶段状态。
