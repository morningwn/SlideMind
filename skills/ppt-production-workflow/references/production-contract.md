# PPT 生产契约

本 reference 用于完整创建、重写或导出任务。它定义阶段输入、产物、门禁和失败处理；中间记录默认保留在会话中，只有用户要求或材料复杂到需要跨轮复用时才写入项目文件。

## 状态机

`intake → evidence-ready → strategy-documented → design-ready → written → structure-verified → exported`

`exported` 是可选终态。用户只要求可编辑稿时，`structure-verified` 即完成。

不得跳过以下转换：

- `intake → evidence-ready`：先确定统一产物目录，读取引用材料并区分事实、推论、建议和待确认项。
- `evidence-ready → strategy-documented`：先验证核心承诺和标题序列，再把任务、证据边界和逐页地图写入独立 Markdown 文档。
- `strategy-documented → design-ready`：模板阶段根据语义页面职责和内容规模分配 PPTist 页面角色，再选择容量匹配的模板页或自定义布局。
- `design-ready → written`：写入前必须取得最新 revision，并证明整份替换不会丢失内容。
- `written → structure-verified`：写入后必须回读，不以工具成功返回代替复核。
- `structure-verified → exported`：只在用户要求 PPTX 且阻塞项已清零时导出。

## 阶段产物

### Artifact directory

目录选择优先级固定为：

1. 用户明确指定的目录名称或项目相对路径；
2. 用户明确指定的交付文件路径的父目录；
3. 根据主题自动生成的 `<topic>-presentation/`；主题无法稳定提取时使用 `presentation-project/`。

自动目录名移除路径分隔符、控制字符和首尾空白，把连续空白折叠为短横线。用户明确名称只做安全校验，不擅自改写语义。目录已经存在且明显属于同一演示时复用；如果包含无关同名产物，选择 `-2`、`-3` 等未占用名称，不覆盖。

统一目录必须位于当前项目内。用户指定项目外目录时，说明工具边界并请求改用项目相对目录；在目录未确定前不要把部分产物写到其他位置。

建议结构如下，实际只创建任务需要的文件：

```text
<artifact-directory>/
├── <topic>-deck-strategy.md
├── <topic>.slides.json
├── <topic>.pptx
├── source-notes.md
├── assets/
└── sources/
```

大纲、可编辑演示、导出文件、来源记录、质量报告、生成图片和下载素材都必须位于该目录或其子目录。构建临时文件用完即丢弃；用户原始材料保留在原位置，不因聚合产物而移动或复制。

### Intake brief

- 受众与已有认知；
- 要促成的决定或行动；
- 场景、时长和语言；
- 输入材料与禁止使用的材料；
- 品牌、模板、页数和文件格式约束；
- 统一产物目录及其命名依据；
- 已采用的保守假设。

### Evidence ledger

每条关键证据记录：事实陈述、来源、日期或版本、口径、可支持的结论、不能支持的外推。用户材料与外部材料分开标记。检索只能填补已识别的缺口，不围绕想要的结论寻找佐证。

### Strategy Markdown

`deck-strategy` 阶段必须生成或更新项目内 `.md` 文件，不生成 `.slides.json` 或 `.pptx`。文档包含任务说明、证据边界、核心承诺、叙事主线、标题序列、逐页地图和待确认问题。

逐页地图为每页记录：顺序、页面职责、结论式标题、证据、视觉形式、内容规模、来源呈现位置、待确认项。它不记录 PPTist 页面角色、模板 ID、候选页索引或节点类型。标题序列是最小可审查叙事；正文不是页面地图的替代品。后续页面制作读取该 Markdown 作为规划输入，但不能把其中的说明文字直接复制到观众可见页面。

### Design contract

记录画布、视觉路线、页边距、网格、字号层级、字体、颜色职责、图片策略和重复元素位置。选择内置模板时，在本阶段完成 PPTist 页面角色映射，并记录模板 ID、页面索引和节点容量；禁止把这些实现字段回写成上游大纲的必填项，也禁止混用两套模板视觉语言。

### QA ledger

问题按以下严重度记录并清零：

1. 阻塞交付：事实错误、内容丢失、revision 冲突、越界、不可保真覆盖、关键占位符；
2. 影响理解：标题与证据不一致、阅读顺序不清、字号或对比风险、流程断边；
3. 视觉瑕疵：轻微对齐、间距或跨页一致性问题；
4. 人工确认：结构数据无法证明的字体替换、真实溢出、裁切和 Office 兼容性。

前三类未处理完不得声称成稿通过。第四类必须在交付说明中保留，除非已经通过真实渲染逐页检查。

## 工具调用序列

### 新建可编辑稿

1. 使用 `write` 把策略 Markdown 写入统一产物目录，由此确保父目录存在
2. 在同一目录调用 `slides_create`
3. `slides_read`
4. `slides_write`，使用刚读取的 revision 和全部页面
5. `slides_read`，完成结构复核
6. 必要时重复“读取 → 修复写入 → 回读”
7. 用户要求 PPTX 时，以同一目录中的显式 output 调用 `slides_export`
8. 可选 `pptx_read` 回读导出内容，验证语义而非渲染

### 修改已有可编辑稿

1. 分段 `slides_read` 直到覆盖全部页面
2. 检查不受支持的元素和无法恢复的样式
3. 合并保留页与修改页
4. 紧邻写入前再次 `slides_read` 获取 revision
5. 单次 `slides_write` 替换全部页面
6. 回读并执行质量审查

如果任一页面包含当前工具无法保真的内容，停止整份写入并给出最小人工修改方案。

### 读取外部 PPTX

使用 `pptx_read` 分段提取文字、备注、表格、图表、公式和媒体摘要。它只能作为内容输入或审查依据，不能建立可编辑导入承诺。需要重建时按新建流程创建 `.slides.json`，并明确复杂格式不会自动保留。

## 停止条件

遇到以下情况暂停相关变更并说明影响：

- 关键事实缺失且不同答案会改变核心结论；
- 用户未授权创建、修改或导出；
- 目标文件存在未合并的外部修改；
- 当前工具无法保留既有复杂元素或精细样式；
- 模板容量与内容冲突且拆页会违反用户硬性页数；
- 用户要求项目外产物目录，当前工具无法安全写入；
- 用户要求真实视觉验收，但当前环境没有渲染或逐页查看能力。

停止只影响被阻塞阶段。仍可交付已完成的上游产物，例如证据缺口清单、标题序列或人工修复建议。
