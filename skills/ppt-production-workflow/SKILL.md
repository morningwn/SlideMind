# PPT 制作总控流程

把演示制作视为有明确状态和验证门槛的生产流程。总控只负责判断当前阶段、加载专项 Skill、维护阶段产物和决定能否进入下一步；不要复制专项 Skill 的规则。

加载专项 Skill 时，从当前可用 Skill 列表按名称解析其实际路径并读取 `SKILL.md`；不要假设各 Skill 之间存在固定的 `../` 目录关系。缺少必需的已注册 Skill 时报告缺失依赖，不得静默改读无关文件。

每个阶段完成后都必须持久化产物并更新 `workflow-status.md`，但是否停止取决于执行模式：

- **连续模式**：用户明确要求完成、新建、重写或交付整份演示，且没有要求逐阶段审阅时使用。安全完成一个阶段后直接进入下一阶段，直到达到用户要求的交付层级或遇到停止条件。
- **审阅模式**：用户要求逐阶段确认、希望先看大纲/文案/设计，或当前关键选择必须由用户决定时使用。完成当前阶段后标记为 `awaiting-review` 并停止。

不要把用户对完整交付的明确授权降级为强制逐阶段确认，也不要因为连续模式而越过事实缺口、覆盖风险或未请求的导出范围。

完整创建、重写或导出前，读取 [references/production-contract.md](references/production-contract.md)。只有在维护或评审本 Skill 时才读取 [references/open-source-foundations.md](references/open-source-foundations.md)。

## 统一产物目录

每个演示任务只使用一个项目内产物目录。用户明确指定项目相对目录名称或路径时以用户选择为准；用户只指定交付文件路径时使用其父目录；均未指定时根据演示主题生成简短、安全、可读的目录名，例如 `<topic>-presentation/`。目录确定后作为整个流程的稳定状态，所有阶段必须复用，不能各自重新命名或把文件散落到项目根目录。

`workflow-status.md`、大纲 Markdown、逐页文案、设计规范、`.slides.json`、按需导出的 `.pptx`、来源记录、质量报告及生成或下载的素材都必须位于该目录下；允许使用目录内的 `assets/`、`sources/` 等子目录。临时文件不作为产物保留，用户提供的原始材料也不移动或复制，除非用户明确要求。

## 任务路由

先确认用户要求的是演示相关工作；普通文案任务退出本流程，按用户所需文体完成，复杂任务使用已注册的 `task-workflow` Skill。材料来自 PPT 并不表示交付物也必须是 PPT。

应用名称、教师身份、项目中已有课件或历史工作流不能作为制作演示的依据。“教学思路”“分析”“总结”默认在对话中回答，不为其创建演示目录、策略文档或状态文件；只有用户明确要求演示或继续已授权的演示任务，才进入下列路由。用户只是重复问题时，不能把此前自行生成的课件当作已批准的目标。

再判断用户实际要求的交付层级：

- 仅梳理演示目标、结构或 PPT 大纲：加载已注册的 `deck-strategy` Skill，默认在对话中提供大纲；用户要求保存时才生成 Markdown 文件，不创建演示文件。
- 仅改写页面文字：加载已注册的 `slide-copywriting` Skill。
- 仅处理数据页：加载已注册的 `data-storytelling` Skill。
- 仅制作流程图：加载已注册的 `slide-flowchart` Skill；按其要求再读取几何 reference。
- 仅选择或套用内置模板：加载已注册的 `pptist-template-library` Skill 及其指定 reference。
- 仅做视觉重设计：加载已注册的 `slide-visual-design` Skill。
- 仅检查或验收：加载已注册的 `deck-quality-review` Skill，默认只报告，不写入。
- 新建、重写或交付完整演示：读取或创建 `workflow-status.md`，从下方第一个未完成或待修改阶段开始，并按执行模式推进。

不要因为用户选择了本 Skill 就自动扩大交付范围。用户只要大纲时仅提供 Markdown 格式的大纲，是否保存按用户要求，不创建 `.slides.json` 或 PPTX；只要可编辑稿时不自动导出 PPTX；只要审查时不自动修复。

## 阶段推进规则

- 新任务先创建 `workflow-status.md`；恢复任务先读取它，并以其中的阶段状态、执行模式和文件路径为准。
- 连续模式下，阶段完成后标记为 `completed`，记录产物、关键假设和检查结果，然后推进到下一阶段；不得提前生成尚未进入阶段的产物。
- 审阅模式下，阶段完成后标记为 `awaiting-review`，列出产物、关键假设、待确认项和下一阶段，然后停止。用户明确确认后标记为 `approved` 并继续。
- 用户提出修改时，把当前阶段标记为 `needs-revision`；修订完成后根据当前执行模式继续或重新提交审阅。
- 上游阶段被修改时，把依赖它的下游阶段标记为 `stale`；必须从最早受影响阶段重新推进，不能沿用旧产物。
- 分阶段不等于逐页覆盖。进入可编辑草稿阶段后，`slides_write` 仍以整份演示为一次原子事务。

## 分阶段流程

### 1. 任务与证据

明确受众、演示目的、期望行动、使用场景、材料范围、语言、品牌或模板约束，以及交付物是 Markdown、`.slides.json`、`.pptx` 中的哪些文件。按“用户目录 → 明确文件的父目录 → 主题生成目录”的优先级确定统一产物目录，创建 `workflow-status.md`，需要时写入 `source-notes.md`。只有会改变核心结论、受众行动或不可逆写入范围的缺口才需要追问；其余使用保守假设并显式说明。审阅模式下完成后停止；连续模式下证据边界稳定后继续。此阶段本身不生成大纲。

写入已有演示前必须确认用户确实要求修改。读取外部 `.pptx` 只使用 `pptx_read`；当前工具不能把外部 PPTX 无损导入或原位编辑，不能暗示已经做到。

先读取全部用户引用材料，再把内容分为事实、推论、建议和待确认项。需要外部检索时只补齐与核心结论直接相关的缺口，记录来源、日期、口径和适用范围；不得用搜索摘要替代原始来源。`web_search` 返回的 `search_excerpt` 是搜索服务片段；使用 `fetch_content` 或 `source_check` 获取原文，再用 `get_search_content` 分页读取。`source_check` 只组织证据，不提供真假判定；抓取失败、缓存过期或未返回正文时保留证据缺口，不推断为已核实。

没有依据的数字、案例、引语或客户评价不得进入后续阶段。来源无法写入备注时，在页面脚注、来源页或项目内伴随文本中保留可追溯信息，不能声称已写入演讲者备注。

### 2. Markdown 大纲

加载已注册的 `deck-strategy` Skill，生成或更新 `<topic>-deck-strategy.md`。文档中形成核心承诺、标题序列和逐页地图；每页至少包含页面职责、结论式标题、支撑证据、视觉形式和待确认项。标题序列不能独立讲清故事时保持本阶段待修改。审阅模式下完成后停止；连续模式下通过自检后继续，但此阶段不生成逐页成稿。

### 3. 逐页文案

加载已注册的 `slide-copywriting` Skill，数据页再加载 `data-storytelling` Skill，流程页再加载 `slide-flowchart` Skill。把观众可见的标题、正文、数据结论、流程节点和来源呈现方式写入 `<topic>-slide-content.md`。审阅模式下完成后停止；连续模式下通过自检后继续。此阶段不选择模板、不调用 `slides_write`。

### 4. 视觉与模板设计

视觉路线只能选一种：

- 用户指定内置模板：加载已注册的 `pptist-template-library` Skill，先按内容角色和容量查询候选页，再映射内容。
- 用户给出明确视觉方向但未指定模板：加载已注册的 `slide-visual-design` Skill，建立统一的网格、字体、颜色和间距系统。
- 编辑已有 `.slides.json`：以现有页面为视觉基准，不混入无关模板；先判断当前元素是否能被工具无损保留。

把视觉系统、模板 ID、PPTist 页面角色、候选页映射、素材需求和关键布局写入 `<topic>-design-spec.md`。模板只能承载已稳定内容，不能决定叙事；容量不足时回到文案阶段拆页或换版式，不压小字号硬塞。审阅模式下完成后停止；连续模式下通过自检后继续。此阶段不创建 `.slides.json`。

### 5. 可编辑草稿

只有大纲、逐页文案和设计规范均为 `completed` 或 `approved`，且没有 `stale` 或关键待确认项时，才在统一产物目录中调用 `slides_create`。`.slides.json` 路径必须位于该目录；任何 `slides_write` 之前都必须立即调用 `slides_read` 并使用其最新 revision。

`slides_write` 会替换全部页面，只在以下条件全部满足时执行：

- 用户已要求创建或修改；
- 页面地图、文案和视觉方案已经稳定；
- 将保留的全部页面都已纳入写入参数；
- 现有复杂元素、富文本和样式可以被当前工具安全表达；
- 不存在未解决的关键事实或外部修改冲突。

使用一次 `slides_write` 写入完整草稿，避免按页反复覆盖。发生 revision 冲突时重新读取、重新合并，不复用旧 revision。写入后立即再次 `slides_read`，核对页数、标题、元素类型、坐标和关键内容。审阅模式下完成后停止；连续模式下结构回读通过后进入质量审查，不能跳过审查直接导出。

### 6. 质量审查

加载已注册的 `deck-quality-review` Skill，对草稿执行叙事、事实、文案、几何、真实渲染和导出准备度检查，把结果写入 `<topic>-quality-report.md`。审阅模式下发现问题后停止，等待用户决定是否修复；连续模式下可以修复已明确且可安全修复的问题，并重新审查受影响页面，最多执行两轮修复—复审。两轮后仍有阻塞项时停止并报告，不得无限重试。审查通过后，只有连续模式且用户已要求 PPTX 时才进入导出。

### 7. PPTX 导出

只有质量审查为 `completed` 或 `approved` 且用户已要求 PPTX 时才调用 `slides_export`，并显式把输出路径设为统一产物目录中的 `.pptx`，不要依赖默认输出位置。审阅模式还需要用户确认审查结果后才能导出。导出后可用 `pptx_read` 回读语义内容，但这不能证明字体替换、文字溢出、图片裁切或 PowerPoint 兼容性已经通过。完成后更新状态为 `exported`。

## 完成标准

- 交付范围与用户请求一致，没有擅自多做文件或导出；
- `workflow-status.md` 记录所有已完成阶段的用户批准状态，且不存在影响当前交付物的 `stale` 阶段；
- 标题序列构成完整论证，关键结论有证据或假设标记；
- 演示策略和逐页地图保存在独立 Markdown 文档中，不混入演示 JSON；
- 所有持久产物位于同一个用户指定或按主题生成的目录中；
- 页面容量、坐标、层级和元素类型通过结构复核；
- 没有遗留占位符、伪造来源、未解释数字或已知冲突；
- 可编辑源文件是 `.slides.json`，`.pptx` 被视为派生交付物；
- 最终回复列出生成或修改的文件、已执行的检查，以及仍需人工视觉确认的限制。
